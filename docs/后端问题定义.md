# 后端问题定义 · CookCoach 导师服务（魏伊林）

## 背景
Unity 已知道玩家在哪一步、炉火状态、哪个操作成功/受阻。后端负责让真实模型读懂这些信息，给出符合当下的指导。契约样例见 `shared/*.example.json`，接口约定见 `组员联调交接.md`。目前 `backend/` 目录尚不存在，需新建。

## 范围
1. `backend/` FastAPI 服务（Python 3.12）：
   - `GET /health` → `{"status":"ok"}`
   - `POST /api/v1/guidance`：接收快照 + 最近 10 操作 + 最近 6 轮对话 + 玩家问题 → 调真实模型（DeepSeek API，调用层按 OpenAI 兼容格式写）→ 返回一句指导 + 可选高亮编号
2. 上下文组装与提示词（含 S6 `snapshot.finish_phase` 四分支：熟蛋回锅 / 合炒 / 关火 / 装盘）
3. fallback 路径（模型超时或不可用，按步骤规则表返回备用提示）
4. 按 `request_id` 留 JSONL 日志（`backend/logs/`，每请求一行）：实际模型输入、原始输出、校验结果、耗时
5. `requirements.txt` + `.env.example` + 启动说明
6. 自测 + 两条真实轨迹证据

## 最终交付物
- `backend/`：可运行服务、依赖清单、`.env.example`（不含真实密钥）
- 日志文件：按 `request_id` 可查模型输入/输出/校验/耗时，与客户端保存的 JSON 编号对齐
- 给朱玉的交付包：启动命令、接口地址 `http://127.0.0.1:8000`、一次真实的「出错→追问」请求与回复
- 经 PR 合入 `main` 的代码

## 硬约束（违反即联调失败）
- 请求/回复字段与 `shared/` 样例完全一致；改字段须同步 `shared/` 并通知组员
- 原样回传 `request_id`、`session_id`、`state_version`
- `source`：真实调用 = `llm`；超时/不可用 = `fallback`（不是 5xx）；`guidance.message` 必须非空
- `highlight_target_id` 只能从本次请求的 `allowed_highlight_targets` 中选，否则留空
- `trigger` ∈ {error, hint, question}；`hint_level` ∈ {check, explain, direct}
- 整个响应 < 20 秒（客户端超时即丢弃），模型调用内部超时 10 秒，超时走 fallback
- UTF-8 JSON；密钥只在后端本地环境变量，绝不入库
- S6 必须读 `finish_phase` 区分回锅/合炒/关火/装盘，不能凭"最后一步"猜

## 隐含要求（图中没写但必须做到）
- 追问要结合历史：「开关在哪？」→ 简短位置提示 + 高亮 `stove_switch`；开火后再问 → 按新炉火状态回答
- 指导是一句中文短句，导师口吻；受阻时能结合 `reason`（如 `stove_off`）讲清错在哪
- 模型输出无论好坏，结构校验必须通过（高亮钳制、message 非空、枚举合法）
- 服务无状态：上下文全部来自请求本身，多会话、并发重试不串扰
- 模型故障时宁可 fallback 也不挂起或报错（客户端依赖 fallback 语义 + 手动重试）
- 构造模型输入时自设 token 预算，防御性截断（客户端已限 10 事件/6 轮，后端仍要兜底）
- 本地 Windows 可跑，联调期间地址稳定

## 什么叫完成（验收标准）
1. `shared/` 两份样例打真实服务，回包结构与字段合法
2. 真实模型走通验收轨迹：打蛋→切番茄→未开火炒蛋受阻→提示先开火；追问「开关在哪」→高亮旋钮；开火后再问→提示倒蛋；S6 四个 finish_phase 提示各对
3. 模拟模型不可用：返回 `fallback` + 非空提示，且 < 20 秒
4. 日志与客户端导出记录按同一 `request_id` 核对一致
5. 朱玉按交付包接入同一入口联调通过；最终报告标出厨房输入来源、回复来源、执行结果、测试版本
6. 无密钥入库，PR 合入 `main`

## 最容易翻车的风险点（按概率×损失）
1. **DeepSeek 密钥/额度不可用**：整体阻塞，开工第一步先做一次真实调用冒烟验证
2. **20 秒超时没兜底**：客户端丢回复，联调时看起来像后端坏了
3. **回传三兄弟/字段/枚举错一个**：客户端对不上轮次，直接不可用
4. **模型无视状态**：给出通用做菜建议、忽略 `finish_phase`，验收轨迹不过
5. **fallback 做成 500 或空消息**：破坏客户端的重试体验
6. **密钥/环境变量不文档化**：组员跑不起来，`.env.example` 缺失（README 已引用但不存在）
7. **违反仓库协作规则**：改 `shared/` 不通知、提交 `.env`、直推 `main`
8. **端口混淆**：真实服务 8000 与 fixture 18741 并存，Unity 端 Endpoint 填错会连到 mock 服务

## 已确认（2026-11-24）
1. 模型：DeepSeek API；调用层按 OpenAI 兼容格式写，之后换 provider 只改配置。模型名默认 `deepseek-chat`，10 秒预算下不用 reasoner
2. 端口与绑定：`127.0.0.1:8000`，与朱玉同机联调
3. fallback：按步骤规则表（current_step / finish_phase 分支，参考 fixture 思路）
4. 日志：`backend/logs/` 下 JSONL 文件，每请求一行，含模型输入/原始输出/校验/耗时
5. 模型内部超时：10 秒，超时即 fallback

## 建议执行顺序
DeepSeek 密钥冒烟 → 服务骨架 + 契约测试（以 shared 样例当 fixture）→ 提示词 + DeepSeek 联调（先过 3 条验收轨迹）→ fallback 规则表 + JSONL 日志 → 全量自测 → 交付朱玉联调 → PR
